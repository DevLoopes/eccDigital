# v0.1.0 — Estrutura base do monorepo e arquitetura inicial

> Esta é uma tag inicial que representa a fundação do projeto: estrutura monorepo, API, frontend, banco de dados e organização modular em evolução.

## Visão geral do projeto

Este repositório foi organizado como um monorepo, com três principais blocos de responsabilidade:

- API: aplicação de backend em Node.js e TypeScript
- Web: frontend em Next.js
- Database: pacote compartilhado para schema e integração com PostgreSQL

A stack base combina produtividade, modularidade e clareza arquitetural. O uso de pnpm + Turbo permite gerenciar múltiplos aplicativos em um único repositório, compartilhando dependências e automatizando scripts de desenvolvimento e build.

## Ferramentas e tecnologias utilizadas na estrutura base

### 1. pnpm + Turbo Repo

- O projeto usa pnpm como gerenciador de pacotes.
- O Turbo coordena scripts de desenvolvimento, build e lint em todos os apps do monorepo.
- Isso facilita o trabalho em múltiplos projetos com uma única interface de execução.

### 2. TypeScript

- A base do projeto é escrita em TypeScript em todos os módulos.
- Isso melhora segurança de tipos, manutenção e previsibilidade em APIs, frontend e esquema do banco.

### 3. Express no back-end

- A API usa Express como framework HTTP principal.
- A aplicação é inicializada em um bootstrap central que cria o servidor, aplica middleware de JSON e monta as rotas dos módulos.
- O uso de Express permite uma estrutura simples e clara para expor endpoints REST.

### 4. Zod

- A validação de entrada dos dados da API é feita com Zod.
- Isso garante que payloads vindos do cliente tenham estrutura correta antes de entrarem na lógica de negócio.

### 5. Next.js no frontend

- O front-end é construído com Next.js, usando a estrutura de App Router.
- A aplicação monta o layout principal em um componente de raíz e organiza páginas em módulos dentro da pasta app.
- O uso de Next.js oferece renderização moderna, suporte a layout, fontes e arquitetura de páginas organizada.

### 6. Tailwind CSS e componentes visuais

- O frontend utiliza Tailwind para estilização.
- Também há integração com shadcn/ui, patterns de componentes e utilitários para construção de interfaces consistentes.
- O projeto já demonstra uma abordagem moderna para UI, sem depender de CSS pesado manual.

### 7. PostgreSQL + Docker Compose

- A base de dados é PostgreSQL.
- O ambiente de desenvolvimento é provisionado por Docker Compose com um container postgres-db.
- Isso facilita a reprodução do ambiente local e a integração consistente entre backend e banco.

### 8. Drizzle ORM

- O banco é acessado via Drizzle ORM, uma solução leve e tipada para TypeScript.
- O ORM é usado para modelar tabelas, construir queries e manter a comunicação com o PostgreSQL em um estilo declarativo.
- A estrutura favorece manutenção, clareza e segurança no acesso ao banco.

### 9. dotenv

- O projeto usa variáveis de ambiente para configurar porta, string de conexão e parâmetros do banco.
- Essa abordagem centraliza a configuração externa e deixa a aplicação mais segura e reutilizável.

## Arquitetura Hexagonal e organização por módulos

A estrutura do backend segue fortemente o padrão de Arquitetura Hexagonal, também conhecida como Ports and Adapters.

### Princípio central

A ideia principal é separar:

- o domínio da aplicação
- a lógica de negócio
- e as tecnologias externas, como banco e HTTP

Isso reduz acoplamento e torna o sistema mais testável e extensível.

### Camadas da arquitetura no projeto

#### Domain

Nesta camada ficam:

- entidades do negócio
- regras centrais
- contratos de repositórios
- serviços de domínio

Um exemplo claro é a entidade de usuário, que representa o modelo do negócio sem depender de banco ou HTTP.

#### Application

Aqui ficam os casos de uso da aplicação, como criação, leitura e regras de orquestração.

O uso de caso atua como ponte entre:

- entrada de dados
- regras de domínio
- e a infraestrutura necessária para persistência

#### Adapters

São os adaptadores que conectam o sistema ao mundo externo.

Existem dois grandes tipos:

- inbound adapters: controladores e rotas HTTP
- outbound adapters: repositórios e integrações com banco de dados

No projeto, isso aparece claramente:

- o controller expõe rotas REST
- o repositório implementa a persistência com Drizzle
- o mapper converte entre entidade de domínio e estrutura de persistência

## Módulo molde: padrão domain / application / adapters

O módulo de usuários funciona como exemplo base para a organização do projeto.

### Estrutura do módulo Users

- domain
  - entities
  - repositories
  - services
- application
  - ports
  - use-cases
- adapters
  - inbound
    - http
  - outbound
    - persistence
    - mappers

Essa separação mostra o padrão usado em todo o backend:

- Domain: modelo e regras de negócio
- Application: casos de uso e contratos
- Adapters: entrada via HTTP e saída via banco

Esse formato é a base para expandir o sistema para outros módulos e entidades, como categorias, transações, autenticação e regras financeiras.

## Backend: Express HTTP e estrutura de bootstrap

A API é montada por um módulo principal de aplicação que:

- cria a instância do Express
- habilita JSON
- conecta os módulos da aplicação
- associa rotas

A estrutura de bootstrap deixa o servidor centralizado e facilita a injeção de dependências. Em outras palavras, a aplicação não “hardcodeia” repositórios diretamente na camada HTTP; ela constrói o módulo e injeta a implementação concreta.

Isso é um ponto forte da arquitetura, porque:

- o controller não conhece detalhes do banco
- o serviço não conhece detalhes da rede
- a infraestrutura fica isolada da lógica principal

## Frontend: Next.js e layout modular

No frontend, a aplicação em Next.js usa um layout principal que organiza:

- metadados da aplicação
- fontes globais
- classes base e estilos gerais
- estrutura de página

A estrutura do app segue uma lógica moderna de organização por módulos, com:

- layout global
- páginas e componentes
- recursos e utilities compartilhados
- estilos globais

O uso de Next.js também deixa o projeto preparado para evolução em UI, percurso de autenticação, dashboards, formulários, consumo da API e integração com serviços externos.

## Banco de dados: schema, Drizzle e integração com Postgres

A camada de dados possui uma responsabilidade bem definida:

### Shared database package

O pacote compartilhado de banco centraliza:

- cliente de conexão
- schema
- utilitários de acesso
- migrações e geração de SQL

### Schema modelado em Drizzle

O schema define tabelas como:

- usuários
- categorias
- transações

Com tipos e relações importantes, como:

- UUID como chave primária
- relacionamento entre usuário e categoria
- relacionamento entre usuário e transação
- índices para consultas
- validações de negócio no nível do banco

### Integração com Postgres

A conexão é feita com:

- PostgreSQL
- driver de Node
- Drizzle ORM

A variável de ambiente DATABASE_URL conecta a aplicação ao banco, e o Docker Compose garante um ambiente local pronto para uso.

Esse desenho deixa a persistência separada do restante da aplicação, o que é essencial para manter a arquitetura limpa e escalável.

## Conclusão da tag inicial

A tag inicial do projeto representa a base estrutural do sistema, com:

- monorepo organizado
- backend em Express + TypeScript
- frontend em Next.js
- banco PostgreSQL com Drizzle
- arquitetura hexagonal bem definida
- padrão modular de domínio, aplicação e adapters
- infraestrutura pronta para evoluir para funcionalidades reais do produto

Em resumo, esta versão é a “fundação do sistema”: a base da aplicação está pronta para receber CRUDs, regras de negócio, autenticação, integrações e crescimento da solução.
